# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SAFI is a legacy PHP monolith for Inglosa (Inversiones Globales, S.A. de C.V.) — vehicle sales, service/repair shops, inventory, appointments, insurance claims ("averías"), and integration with SAP. Procedural PHP, no framework, no build step, no autoloader beyond Composer for two libraries. Backend, HTML, and JS are mixed in the same files throughout.

**Repo root** is one level above this directory (`C:\DEV-git\SAFI`, `git rev-parse --show-toplevel`). This `www/` folder is the Apache document root and holds virtually all application code. Siblings at the repo root:
- `vendor/` — Composer packages for `phpoffice/phpword` (root `composer.json`).
- `www/vendor/` — a **separate** Composer install for `aws/aws-sdk-php` (`www/composer.json`). Two vendor trees exist; don't assume one covers both.
- `plantillas/` — DOCX templates (`TemplateProcessor`) used to generate sale contracts.
- `sql/` (root) and `www/sql/` — both exist; migrations for this session's work went in `www/sql/`.
- `backup/` — timestamped manual backups of specific fixes, not a tool-managed directory.

## Running it locally

There is no dev server task, build, lint, or test suite in this repo. Development happens directly against XAMPP:
- PHP binary: `C:\xampp\php\php.exe`, ini at `C:\xampp\php\php.ini` — **this same php.ini is used by both CLI and Apache's PHP module** here (no separate `PHPIniDir` in `httpd-xampp.conf`), so checking an extension via CLI (`php -m`) reliably tells you what Apache sees too.
- `zip` extension is commented out in that php.ini. This breaks `PhpOffice\PhpWord\TemplateProcessor` (DOCX is a zip) used for contract PDF generation — fails locally with `Class "ZipArchive" not found`. Production has it enabled. Don't "fix" the local php.ini without asking; it's an environment gap, not a code bug.
- Contract PDFs are generated by writing a DOCX from a template in `plantillas/`, then shelling out to LibreOffice (`soffice --headless --convert-to pdf`) — see `getSofficeCommandDev()`/`getSofficeCommandProd()` and `convertirDocxAPdf()` (duplicated in `vehiculos_reparacion_mant.php` and `ventas_mant_contrato.php`).
- `include/config.php` (local/dev) and `include/config_inglosa_produccion.php` (production) are both gitignored and **not present in a fresh checkout** — the app will not run without one. They are swapped manually at deploy time, not selected by any code path. Constants defined there include DB credentials (`db_ip`, `db_name`, `db_user`, `db_pw`), mail, and `app_openai_api_key` / `app_openai_model` (OpenAI Chat Completions, used by `include/ia_comprobantes.php`).
- Real login/session (`_SESSION['usuario']`, `_SESSION['seg']` permission list, plus signed `urs`/`sgt` cookies checked in `verificar_cookie()`) is required for almost every page. To exercise DB-backed logic from the CLI without a browser, write a throwaway script that fakes `$_SERVER['HTTP_USER_AGENT']`, matching `sgt`/`urs` cookies, and a `$_SESSION` array (`usuario`, `usuario_id`, `seg` as the permission-id array, `formato_fecha`, `hora_ultima_tran`) before requiring `include/framework.php` — this is the pattern used throughout this project's sessions for real verification against the live DB. Delete these scripts when done; never commit them.

## Verifying a change (there is no test suite)

- `php -l path/to/file.php` for syntax.
- For a `<script>` block embedded in a `.php` file: extract the exact line range (`sed -n 'start,endp'`), substitute any `<?php echo ...; ?>` fragments with a literal placeholder value, then `node --check` the result.
- For anything touching the DB: run it for real via the CLI-with-faked-session technique above against the live DB (`db_ip`/`db_name` in `include/config.php`) — this codebase has no fixtures/seed data, so "real row, read it back" is the only reliable check.
- No CSS/JS bundler: `plugins/` (Bootstrap 4, jQuery, jQuery File Upload, SweetAlert2, DataTables, Select2, Chart.js, Font Awesome, fabric.js, ...) are vendored copies loaded via `<script>`/`<link>` tags, not npm packages. Check the vendored version before assuming a modern API — e.g. **SweetAlert2 here is v9.10.8**, which uses `onOpen`/`onClose` (not `didOpen`/`didClose`) and a result object with `.value`/`.dismiss` (not `.isConfirmed`/`.isDenied`). Silently-ignored unknown options are a real failure mode: passing a newer option name does nothing and no error is raised.

## Core architecture

- `include/framework.php` is the one file almost everything depends on: session/cookie handling and expiry (`sesion_expirada()`), permission checks (`tiene_permiso($id)` / `pagina_permiso($id)` against `$_SESSION['seg']`), DB helpers (`sql_select`, `sql_insert`, `sql_update`, `sql_delete`, `get_dato_sql`, `GetSQLValue` — string-built SQL, no prepared statements), generic input validation (`validar($campo, $input, $type, $requerido)`), date/number formatting and Spanish number-to-words helpers, and HTML-widget generators (`campo(...)`, `campo_upload(...)`, `crear_datatable(...)`) used to render form fields consistently across every module. Several stale copies live alongside it (`framework copy.php`, `framework_old.php`, `framework_old2.php`, `framework26032025.php`) — **ignore these**, only `include/framework.php` is live. `include/framework_cron.php` is a trimmed variant for the SAP sync scripts, which run headless via Task Scheduler, not through a browser session.
- **Action routing convention**: most `*_mant.php` / `*_mant_*.php` files are self-routing — they read `$_REQUEST['a']` (view/`v`, guardar/`g`, borrar/`d`, or a bespoke verb) at the top and either `exit` after `echo json_encode(...)`/`salida_json($stud_arr)` for an AJAX action, or fall through to render the full HTML form/tabs. `salida_json()` wraps the response as `[{"pcode":0|1, "pmsg": "..."}]`; `pcode=1` is success.
- **Standalone "program" pattern**: rather than growing one giant `_mant.php` file, self-contained sibling files (e.g. `ventas_comprobantes_pago.php`, `ventas_fotos_web.php`, `ventas_historial.php`, `ventas_contrato_historial.php`) are `require_once('include/framework.php')` on their own and get pulled into a tab's `<div>` via jQuery `.load('file.php?cid=' + id)` from the parent screen's tab-switch handler (each `_mant.php` defines its own `ventas_cambiartab(eltab)`-style function). These mini-programs take the parent record's id as `cid` and implement the same `$_REQUEST['a']` routing independently. When asked to add a tab/feature that already exists elsewhere (e.g. "add the same Comprobantes de Pago tab to X"), check whether the target screen can just load the existing standalone program via `cid` rather than reimplementing it — most of these programs only assume `id_venta`/`ventas`, not which parent screen loaded them.
- **Domain prefixes**: `ventas_*` (vehicle sales + contracts), `averia_*` (insurance/damage claims), `inspeccion_*` (vehicle inspections), `cita_*`/`citas/` (appointments — `citas/` is a separate self-contained sub-app with its own `index.php`/css/js), `traslados/` (vehicle transfers — also self-contained, with its own `framework.php`/`config.php`), `cotizacion_*` (quotes), `servicio_*` / `combustible_*` / `compra_*`. `SAP/` is a deployment package (not app code) for two scheduled sync scripts (`sincronizar.php`, `sincronizar_ordenes.php`) that pull products/vehicles/clients/providers from SAP and push purchase orders/invoices back — see `SAP/instrucciones.txt`.
- **Screens embedded as Bootstrap modals**: many "editar registro" screens are opened via `modalwindow2(titulo, url)` (in `js/app5.js`) into a shared `#ModalWindow2`, loaded by AJAX — the screen's own tabs then live *inside* that modal. Opening a second real Bootstrap modal from a tab inside `#ModalWindow2` is unreliable in this app's Bootstrap 4 (scroll lock, z-index, keyboard-focus trapping all broke in practice) — prefer SweetAlert2 for a dialog shown from a screen that is itself already a modal (see `js/app5.js`'s `show.bs.modal`/`shown.bs.modal` z-index patch for the cases where a nested Bootstrap modal is unavoidable, and `ventas_cambiartab()` closing any `.tab-pane .modal.show` before switching tabs).
- **File uploads**: local disk under `www/uploa_d/` (general) and `www/uploa_d_ventas/` (vehicle sales), both gitignored; `campo_upload()`/the jQuery File Upload plugin (`plugins/fileupload/`) handle the widget, thumbnails are generated with GD (verify GD/relevant extensions before assuming thumbnails exist — missing-thumbnail `<img>` tags with no `file_exists()` guard have caused real bugs). There is also an S3 fallback path (`s3_bucket/`, `aws_bucket_s3`) used in some flows.
- **AI extraction module** (`include/ia_comprobantes.php`): calls the OpenAI Chat Completions API directly over cURL with a bundled CA bundle (`include/cacert.pem`, needed because XAMPP/embedded PHP on Windows often lacks a configured root CA store), `temperature: 0` and `response_format: json_object` for deterministic, parseable output, model from `app_openai_model`. Each document type gets its own narrowly-scoped prompt function (e.g. `extraer_datos_comprobante_ia`, `extraer_datos_recibo_ia`) funneled through the shared `ia_leer_documento_con_ia()` (handles base64 encoding, image vs. PDF content blocks, and lenient JSON parsing). Treat AI output as adversarial input: this module's real save paths re-run the extraction at save time and compare against submitted values (`verificar_comprobante_no_modificado()`) because client-side `readonly` on AI-populated fields is cosmetic only.
- PHP gotcha that has bitten this codebase: `ctype_digit()`/`ctype_alpha()`/`ctype_alnum()` given a raw PHP int between -128 and 255 interpret it as an ASCII code, not its decimal string — always cast to `(string)` first (see `validar()` in `framework.php`).
